Autoridad y evidencia · 02

Quién determina qué cambió

La responsabilidad de comprobar un efecto corresponde al dominio cuyo estado se ha cambiado. La ubicación del dato o el nombre del componente no deciden esa responsabilidad.

Una misma herramienta puede ejecutar operaciones de varios dominios. Cada dominio conserva las reglas de sus efectos.

Responsabilidad del dominio

La autoridad sigue al efecto.

Una operación sobre Git depende del repositorio, la base, las refs y los objetos pertinentes. Una publicación depende de qué artefacto queda visible. Una operación de host depende de su estado efectivo y de las observaciones necesarias para comprobarlo.

Las tres pueden utilizar un shell, una API o el mismo mecanismo de ejecución. Eso no convierte sus efectos en la misma cosa ni obliga a compartir un workflow.

Guardar y mostrar son responsabilidades útiles.

Un registro conserva lo recibido y su procedencia. Una cola puede registrar entregas. Un Dashboard muestra una proyección del estado. Esas funciones ayudan a consultar y reconstruir lo ocurrido; no convierten automáticamente una afirmación recibida en un hecho comprobado del dominio.

Guardar una afirmación ≠ comprobar su efectoResponsabilidad ≠ servicio separado

Una proyección que muestra PASS no añade una comprobación nueva. Para interpretar ese resultado importan el objeto comprobado, el método y los límites de la evidencia que lo respalda.

Permisos antes del efecto.

El dominio comprueba los permisos técnicos, el alcance y las condiciones aplicables. La conversación puede preparar una petición; el nombre de un rol, la prosa o un informe no sustituyen el límite técnico donde se ejecuta la operación.

Cuando la política exige asentimiento humano, se conserva qué se presentó y qué respuesta se recibió. Ese registro no autentica por sí solo a la persona física ni amplía los permisos de ejecución.

Recuperar también depende del dominio.

Determinar qué cambió y decidir cómo continuar son preguntas relacionadas. Si el efecto es incierto, el dominio consulta y reconcilia antes de repetir. Las condiciones para recuperar una operación Git no tienen por qué ser las mismas que para una publicación o un cambio de host.

Responsabilidades integrables

El core no prescribe una topología.

Un proceso puede reunir varias responsabilidades. Petición, admisión, resultado y recuperación aplicable no imponen cuatro servicios, cuatro objetos ni un almacén universal de trabajos.

Alcance. Estos principios forman parte del core mínimo vigente. Explican responsabilidades y límites; no acreditan por sí solos la implementación del nuevo motor RepoOps ni de otros dominios.

Comprobación del efecto y decisiones adicionales

Comprobar que un cambio existe no concede por sí solo permiso para otra operación. Cada efecto posterior conserva su propia admisión y las condiciones que le correspondan.

Una aprobación humana es condicional a la política. Este principio no establece una etapa universal de aceptación después de cada resultado ni exige una autoridad física separada.

RepoOps ilustra el caso de los repositorios. Sus mecanismos Git no se convierten por ello en una capa universal de verdad para todos los dominios.
